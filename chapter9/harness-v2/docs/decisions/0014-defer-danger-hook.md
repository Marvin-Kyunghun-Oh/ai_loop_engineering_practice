# 0014. 위험 명령 차단 훅(C2)은 스모크 테스트 뒤로 미룬다

- 상태: 확정
- 날짜: 2026-11-24

## 맥락
- C2는 generator의 무인 실행에 PreToolUse 훅(chapter4의 `block-dangerous.sh`, `rm -rf` 차단)을 2차 방어로 두자는 항목이다(IMPROVEMENTS C2).
- 0008의 허용 목록이 1차 방어다. 목록 밖의 쓰기 명령(`rm -rf` 포함)은 이미 거부되는 것을 확인했다. 훅은 허용 패턴 안에 위험한 인자가 들어오는 드문 경우만 더 막는다.
- 설치 방식 두 가지를 검토했다. 사용자가 이렇게 정리했다.
  - 에이전트 실행에는 하네스가 `--settings`로 훅을 넘기는 것으로 충분하다.
  - 사람이 조절하고 싶은 훅은 사람이 직접 설계해 대상 프로젝트의 `.claude/settings.json`에 둔다.

## 결정
- 10단계에서 훅을 만들지 않는다. **11단계 스모크 테스트 뒤**에 필요한지 다시 판단한다. 0013(Bash 허용 목록 훅)과 같은 시점이다.
- 그때 만들게 되면 설계는 다음과 같다.
  - 하네스가 훅 스크립트를 `.harness/hooks/`에 실행할 때마다 새로 쓴다. 하네스가 소유하는 생성물이고 사람이 편집하지 않는다.
  - 하네스가 `--settings`로 훅 설정을 넘긴다. 대상 프로젝트의 파일은 건드리지 않는다.
  - 사람의 규칙은 대상 프로젝트의 `.claude/settings.json`에 사람이 직접 둔다. `--settings`와 합쳐져 적용되는지는 만들 때 실제 claude로 확인한다(haiku 1~2회, 약 $0.005).

## 검토한 대안
- **하네스가 훅을 보존하고 사람이 고치게 함**(덮어쓰지 않는 규칙 포함): 하네스 기본값과 사람의 규칙이 한 파일에 섞인다. 과한 설계라서 철회했다.
- **프로젝트에 사람이 설치하고 하네스는 검사만 함**: 설치를 잊으면 시작이 막혀 사람의 개입이 늘어난다. 루프 엔지니어링의 목적(사람의 개입 최소화)에 맞지 않는다.

## 영향
- 당분간 generator는 허용 패턴 안의 위험한 인자를 훅으로 막지 못한다. 목록 밖 쓰기 명령은 계속 거부된다.
- 스모크 테스트의 `permission_denials`와 원본 로그에서 실제 위험 동작이 있었는지 근거를 모은다.
