## 프롬프트

이 요청은 질의응답 3번을 거쳐 나온 결정이다. 흐름 순서대로 적는다.

1. "fatch(수집)은 백그라운드에서 수집하도록 되어있어?"
2. "`claude -p` 실행은 병렬실행이야?"
3. "재구성을 병렬로 바꾸면 속도에서 메리트를 체감할 수 있다는거지?"
4. **(요청 본문)**

```
그러면 일단 병렬은 보류로 할게.
대신 fetch now 뒤에 "수집 중..." 상태를 보여주고, 완료 시 자동으로 새로고침 되도록 개선해줘.
당연히 관련 테스트도 모두 통과되어야 하고,
지금 나의 결정사항의 맥락을 알 수 있도록 (프롬프트)로 잘 정리도 해줘.
```

## 답변

### 1. 결정 맥락 (왜 이렇게 정했나)

| 질문 | 확인한 사실 | 사용자의 결정 |
|---|---|---|
| 수집이 백그라운드인가 | 예. 자동 수집은 APScheduler 스레드, 수동 수집은 이벤트 루프 태스크로 시작하고 즉시 202/303을 응답한다. 동시 실행은 `fetch_lock`이 막는다(409). 단, **진행 상황은 화면에 나오지 않았다.** | 이 단점을 고친다(이번 작업) |
| `claude -p`는 병렬인가 | 사이클 안에서는 **순차**다(요약은 카테고리 중복을 막으려고 한 건씩, 재구성은 카테고리별로 순차). 병렬인 것은 피드 다운로드(최대 5)뿐이다. 병합 직후 재구성만 사이클과 겹칠 수 있다(미해결). | — |
| 재구성을 병렬로 바꾸면 빨라지나 | 하루 30개 기준 요약 30회 + 재구성 5~10회라 재구성은 전체의 일부다. 동시 3개면 전체 20% 안팎 단축으로 **추정**(측정 없음). rate limit 위험도 있다. 병목은 오히려 요약 쪽이다. | **병렬화는 보류.** 먼저 `/logs`의 `started_at`/`finished_at`으로 요약·재구성 시간을 재고, 재구성이 병목이면 그때 동시 2~3개로 적용 |

보류한 것(나중에 다시 볼 후보): 재구성 병렬화(동시 2~3개), 병합 재구성과 사이클의 겹침 방지(`fetch_lock` 공유), 요약 배치 호출.

### 2. 구현한 것
- **서버**: `CycleController.status()`와 `GET /api/fetch/status`(JSON: `running`, `last_error`, `last_report`, `Cache-Control: no-store`).
- **화면**(`base.html`, 바닐라 JS, PRD의 "JS 프레임워크 없음" 유지):
  - 모든 화면 상단에 "수집 중… 끝나면 자동으로 새로고침됩니다." 배너(스피너)를 표시하고 *Fetch now* 버튼을 잠근다. 2초마다 폴링한다.
  - 끝나면 **정확히 한 번** 새로고침하고, 새로고침 뒤에 결과("수집 완료: 새 글 N개, 요약 N개, 위키 갱신 N개", 실패가 있으면 오류색과 건수)를 15초간 보여 준다.
  - 스케줄러가 시작한 수집도 화면을 열어 두면 똑같이 보인다. 서버가 잠시 안 되면 조용히 5초 뒤 재시도한다.
  - 새로고침 반복을 막으려고 `sessionStorage`의 `rssWikiFetch`를 `pending` → `done:…`으로 **새로고침 전에** 바꾼다. 누르자마자 사이클이 끝나 버린 경우도 처리한다.

### 4. 중간에 부딪힌 문제
- 기존 XSS 테스트 `test_html_escaped`가 페이지 전체에서 `<script>`가 없다고 단언했는데, 이제 페이지에 우리 스크립트가 있어서 실패했다. 주입한 페이로드(`x=<script>`)가 이스케이프됐는지(`x=&lt;script&gt;`)만 검사하도록 좁혔다. 보안 검증의 의도는 유지된다.
- 제 실수: 임시 파일을 scratchpad가 아닌 `/tmp`에 한 번 만들었다가 바로 삭제했다.

### 5. 검증하지 못한 것
- 실제 브라우저에서의 모양(배너·스피너 스타일)과 새로고침 동작. JS 로직은 node로 흉내 낸 DOM에서만 확인했다.
- 병합 재구성은 `running`에 포함되지 않아 배너가 뜨지 않는다(수집 사이클만 추적).
