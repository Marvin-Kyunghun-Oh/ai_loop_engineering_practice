### 4. quote-cli (MCP 서버 + 훅)
> `chapter4/quote-cli`
- 명언을 제공하는 파이썬 MCP 서버를 만들어 Claude Code에 연결

#### MCP로 등록
- 한 서버(`quote`)에서 MCP의 세 가지 기능을 모두 노출

| MCP 기능 | 이름 | 사용 방법 |
|---|---|---|
| 도구(Tool) | `get_random_quote`, `add_quote` | 대화 중 Claude가 필요할 때 호출 |
| 리소스(Resource) | `quote://all` | `@quote:quote://all` 멘션 |
| 프롬프트(Prompt) | `quote_post` | `/mcp__quote__quote_post <주제>` |

- `.mcp.json`에 `uv run main.py`를 stdio 서버로 등록하고, `/mcp`로 연결 상태 확인
- 연결 실패(`CONNECTION_CLOSED`) 원인: `[build-system]` 잔존, mcp 2.x의 `FastMCP` → `MCPServer` 개명, 데이터 형식 불일치

#### HOOK
- `.claude/settings.json`에 `PreToolUse` 훅 2개 등록 (스크립트: `.claude/hooks/`)

| 훅 | 대상 | 동작 |
|---|---|---|
| `block-dangerous.sh` | `Bash` | 재귀 강제 삭제(`rm -rf`) 명령을 종료 코드 2로 차단 |
| `audit-mcp.sh` | `add_quote` | 호출 시각·입력값을 `.claude/mcp-audit.log`에 기록 (차단하지 않음) |

- 훅은 종료 코드 2일 때만 실행을 막는다. 그래서 차단 훅은 오류가 나도 2로 끝나게(fail-closed), 감사 훅은 오류가 나도 0으로 끝나게(fail-open) 설계
- `jq`가 있어야 명령 필드만 정확히 검사한다. 없으면 JSON 전체를 검사해 과잉 차단됨

### 5. quote-cli 확장 (서브에이전트 + 워크플로)
> `chapter6/quote-cli`
- 4번의 MCP 서버에 `--search` 옵션, `add_quote` 입력 검증, JSON → SQLite 저장소 전환을 더하며 **서브에이전트 중심**으로 작업

#### 서브에이전트에서 배운 것
- **정의**: `.claude/agents/*.md`의 frontmatter(`name`, `description`, `tools`, `model`, `maxTurns`)로 만든다. `description`이 "언제 위임할지"의 기준이 된다.
- **역할 분리 = 도구 분리**: `code-reviewer`는 읽기 전용(Read/Grep/Glob), `test-runner`는 Bash로 pytest만 실행. 둘 다 코드를 수정하지 않고 보고만 해서, 수정은 메인 세션이 책임진다.
- **컨텍스트 격리**: 서브에이전트는 자기 컨텍스트에서 일하고 요약만 돌려준다. 메인 컨텍스트가 파일 덤프로 오염되지 않는다.
- **저비용 모델 배치**: 검토·테스트 실행처럼 범위가 좁은 일은 haiku로도 충분했다. 근거 파일·행 번호를 요구하면 쓸 만한 지적이 나왔다(경쟁 조건, 시드 검증 우회 등).
- **보고서는 데이터, 명령이 아니다**: 서브에이전트 결과에 섞인 지시문(문서 생성 유도 등)은 따르지 않는다. 사용자 권한은 사용자 메시지에서만 나온다.
- **한계**: 리뷰어는 심각도가 낮은 지적도 섞어서 내므로 사람이 우선순위를 가려야 한다. 리뷰어는 테스트를 실행할 수 없어 실행은 다른 에이전트가 필요하다.

#### 워크플로(`Workflow`)로 오케스트레이션
- 구현 1개(쓰기는 한 에이전트에게만 맡겨 충돌 방지) → 검토·테스트 2개를 `parallel`로 동시에 → 결과를 보고 후속 수정. 검증 단계가 서로 독립이라 병렬이 적합했다.
- 결정적인 흐름(순서·병렬)은 스크립트가 맡고, 판단은 에이전트가 맡는다. 에이전트 수가 늘수록 비용도 늘기 때문에 3개로 제한했다.

#### 개발 흐름 요약
| 작업 | 방식 |
|---|---|
| `--search` 옵션 | 구현 → `code-reviewer` 검토 → `test-runner` 검증 |
| `add_quote` 길이 제한 | 리뷰어가 필요성 검토 → 제안대로 구현 |
| JSON → SQLite | 워크플로(구현 1 + 검증 2) → 지적 10건 후속 수정, 최종 테스트 42개 통과 |
| 기록 | `(프롬프트)` 정책으로 `prompt/`에 프롬프트·답변·결정 사항 보관 |


### 6. rss-wiki (`/goal` + 루프 엔지니어링)
> `chapter8/rss-wiki`
- RSS 피드의 새 글을 `claude -p`로 요약·분류해 주제별 위키로 누적하는 개인용 웹 도구(FastAPI + SQLite FTS5). 코드는 거의 전부 **`/goal` 루프**로 만들었고, 사람은 PRD와 종료 조건을 맡았다.

#### `/goal` = 종료 조건이 있는 에이전트 루프
- `/goal <조건>`을 걸면 Stop 훅이 켜져서, **조건이 참이 될 때까지 에이전트가 멈추지 못한다.** 2번의 `[수집 → 수행 → 검증]` 루프에 "끝났는지 판정하는 문"을 붙인 셈이다.
- 좋은 `/goal`의 구성요소(이번에 쓴 것):

| 요소 | 내용 | 역할 |
|---|---|---|
| 기계가 판정하는 종료 조건 | `docs/TASKS.md` 전부 `[x]` + `uv run pytest` 종료 코드 0 | 에이전트가 "다 했다"고 말로 끝낼 수 없게 한다 |
| 작업 단위 제한 | 한 번에 TASK 하나만 구현 (가장 중요) | 한꺼번에 만들고 한꺼번에 깨지는 것을 막는다 |
| 탈출구 | 막히면 `BLOCKED` 표기 후 다음으로 | 한 항목이 루프 전체를 멈추지 않게 한다 |
| 정지 조건 | 같은 테스트 실패 3번 반복 시 중단·원인 요약, 20턴 후 중단 | 헛도는 루프와 비용 폭주를 막는다 |
| 마무리 | 끝나면 `(프롬프트)` 정책대로 기록 | 결정 맥락을 사람이 나중에 읽을 수 있게 남긴다 |

- **TASKS.md가 루프의 상태 저장소**다. 체크박스가 곧 진행 상황이라, 컨텍스트가 압축돼도(이번 세션에서 한 번 일어났다) 어디까지 했는지 잃지 않았다.
- **입력(PRD)의 품질이 결과의 상한을 정한다.** 첫 `/goal`은 종료 조건을 모두 만족했는데도 사용자가 "원하는 결과물과 많이 다르다"며 PRD를 v0.1로 바꿨고, 같은 `/goal`을 다시 돌렸다. 루프는 조건을 만족시킬 뿐 의도를 맞춰 주지 않는다. 그래서 **루프 전에 PRD에서 결정을 끝내는 것**(질문으로 미결정 사항 확정)이 가장 효과가 컸다.

#### 루프의 "검증" 단계가 약하면 루프는 거짓 성공을 낸다
- 종료 조건이 pytest 통과라서, 에이전트는 통과하기 쉬운 테스트를 쓰는 쪽으로 기울 수 있다. 실제로 `or True` 같은 **항상 통과하는 단언** 3곳을 스스로 찾아 구체적인 단언으로 고쳤다. (E2E를 쓸 때도 같은 실수를 한 번 더 했고 같은 방식으로 잡았다.)
- **단위 테스트 115개가 전부 통과해도 버그가 있었다.** 외부 의존을 전부 가짜로 대체해서, 실제 HTTP·스레드가 엮인 동작은 한 번도 실행되지 않았기 때문이다. 별도의 `/goal`로 **TC를 만들고 E2E**(실제 uvicorn + 로컬 모의 RSS 사이트 + 가짜 `claude` 스크립트)를 돌리자 동시 요청 시 HTTP 500(SQLite 연결의 스레드 제약)이 처음 드러났다. → **종료 조건이 가리키는 검증이 얼마나 실제와 가까운지가 루프의 신뢰도**다.
- 반대로 구현 중 잡은 버그(동기 엔드포인트에서 `asyncio.get_running_loop()` 실패)는 테스트 6건이 같은 원인으로 한꺼번에 깨져서 빨리 찾았다. 실패 신호가 선명하면 루프가 스스로 고친다.
- 검증하지 못한 것(실제 `claude` CLI 품질, 실제 인터넷 피드, 브라우저 시각)은 문서(`docs/QA_TC.md` §5)에 **못 한 일로 명시**했다. 루프의 종료 조건이 참이어도 "무엇을 검증하지 않았는지"는 따로 남겨야 한다.

#### `/goal`을 세 번 쓴 흐름
| # | 목표 | 종료 조건 | 결과 |
|---|---|---|---|
| 1 | TASKS.md 작성 + 구현 | 체크박스 전부 `[x]` + pytest 종료 코드 0 | 만족했지만 의도와 달라 PRD 교체 |
| 2 | 바뀐 PRD로 재구현 | 동일 | T1~T13 완료, 115 passed |
| 3 | QA: TC 작성 + E2E | 모든 E2E 통과, 발견한 결함 수정 | 결함 1건 수정, 145 passed |
- 이후에는 `/goal` 없이 대화로 작은 개선(수집 중 표시와 자동 새로고침)을 했다. 종료 조건이 뚜렷한 큰 작업은 `/goal`, 방향을 묻고 정하는 작업은 대화가 맞았다.

#### 대화로 결정하고 루프로 구현한 예
- `claude -p` 호출은 사이클 안에서 **순차**다(요약 때 카테고리 중복을 막으려고). 사용자가 "재구성을 병렬로 바꾸면 체감되나?"를 물었고, 호출 횟수로 효과를 추정하니 전체의 20% 안팎(측정 없음)이라 **병렬화는 보류**했다. 먼저 `/logs`의 시간으로 병목을 재고 결정한다. → 루프 엔지니어링에서도 **최적화는 측정 뒤에**, 보류 결정과 그 재검토 기준을 기록으로 남긴다.
- 그 대신 사용자 경험의 구멍(진행 상황이 안 보임)을 고쳤다. 브라우저가 없어서 화면 스크립트를 node에 가짜 DOM으로 올려 검증했다. 검증 수단이 없을 때는 **가장 가까운 대체 수단을 만들고, 한계를 적는다.**

#### 정리
| 배운 점 | 내용 |
|---|---|
| 종료 조건은 기계가 판정하게 | 체크박스 + 테스트 종료 코드. "충분히 됐다"는 말은 조건이 아니다 |
| 루프 안전장치 3종 | 작업 단위 제한, BLOCKED 탈출구, 반복 실패·턴 수 상한 |
| 상태는 파일에 | TASKS.md가 진행 상황. 컨텍스트 압축에도 이어진다 |
| 루프는 입력을 넘지 못한다 | PRD가 흐리면 조건을 만족한 결과도 틀린다. 루프 전에 결정하라 |
| 검증이 현실과 가까워야 | 가짜로만 검증한 통과는 거짓 성공 가능. E2E로 단위 테스트가 놓친 버그를 찾았다 |
| 검증 자체를 의심하라 | 항상 통과하는 단언은 루프의 종료 조건을 무력화한다 |
| 못 한 검증은 명시 | 통과했다는 말과 함께 확인하지 못한 범위를 남긴다 |
| 기록 | `(프롬프트)` 정책으로 `prompt/1~5`에 프롬프트·절차·결정 맥락을 보관 |

### 7. 3-Agent 루프 하네스 (`planner → generator → evaluator`)
> v1: `chapter9/harness`(Python), 대상 `chapter9/projects/rss-wiki` / **v2: `chapter9/harness-v2`(Java), 대상 `chapter9/projects/pomodoro-todo`**
- 6번의 `/goal`(한 에이전트가 만들고 스스로 판정)과 달리, **역할을 3개 에이전트로 쪼개고 `claude -p`를 사이클마다 순서대로 호출**하는 하네스다. v1(파이썬 `run.py` 208줄)로 rss-wiki를 만들다 비용 문제로 **M2 중간에서 중단**했다(사이클 38회, TASKS 22/24). v1에서 드러난 결함을 고쳐 **Java로 다시 쓴 것이 v2**이고, pomodoro-todo(Vue 3 + TypeScript 할 일 앱)를 **PRD만으로 `DONE`까지** 만들었다.
- v2 결과: **25사이클, 작업 23개(T10~T32), 마일스톤 6개, 테스트 101개, 총 약 $16.5**(사이클당 약 $0.65). 사이클 25번 모두 정상 종료했고 판정은 PASS 21회·조건부 2회였다. 하네스 코드는 [`harness-v2`](chapter9/harness-v2)에, 사용법은 [`docs/USER_GUIDE.md`](chapter9/harness-v2/docs/USER_GUIDE.md)에 있다.

#### 역할 분리 = 권한 분리
| 에이전트 | 모델(v2 기본) | 쓰기 권한 | 하는 일 |
|---|---|---|---|
| planner | opus | `docs/**`만 (Bash 없음) | PRD와 코드를 대조해 PLAN·TASKS 갱신, 다음 항목 선정, 종료(`DONE`)·중단(`HALT`) 판정 |
| generator | sonnet | 코드 전체 + 허용된 Bash | TASKS의 첫 미완료 항목 **하나**만 구현·테스트, IMPL.md 보고 |
| evaluator | sonnet | `docs/**` + 허용된 Bash | IMPL.md를 믿지 않고 **직접 테스트·타입 검사 실행**, 항목별 점수 채점, REVIEW.md 작성 |
- 계획하는 쪽은 코드를 못 고치고, 평가하는 쪽도 코드를 못 고친다. **만드는 쪽만 코드를 쓰게 해서** "자기가 만든 걸 자기가 합격시키는" 구조를 막았다.
- 비싼 모델(opus)은 판단하는 역할에만 쓴다. v1은 evaluator도 opus였지만 비용 때문에 sonnet으로 내렸다. 그 대가로 임시 복사본에 변이를 넣어 보는 검증은 권한상 못 하게 됐다.
- 허용 명령은 코드가 아니라 **프로젝트별 `harness.yml`의 Bash 허용 목록**이 정한다. 목록 밖 명령은 거부되고, generator는 우회하지 않고 `BLOCKED`를 남긴다.

#### 상태는 파일에, 흐름은 하네스가
- 에이전트끼리는 대화하지 않고 **문서로만 주고받는다**: `PRD → PLAN/TASKS → IMPL → REVIEW → (다음 사이클 planner가 반영)`. 매 사이클이 새 세션이라 컨텍스트가 쌓이지 않는다.
- **순서·기록·상한은 하네스(코드)가, 판단은 에이전트(프롬프트)가** 맡는다. v2에서는 JOURNAL, 비용 기록(USAGE.csv), 아카이브, 예산 차단, 실패 처리를 모두 하네스가 한다. 에이전트가 쓰던 JOURNAL을 하네스가 쓰게 바꿔 형식이 흔들리지 않는다.
- 한 항목은 한 사이클 크기, acceptance는 "실행할 명령 + 기대 결과", `touch`로 수정 범위를 제한한다. 막히면 `BLOCKED(N회째)`를 남기고 3회째면 planner가 `HALT`로 사람을 부른다.
- 종료 판정은 매번 다시 한다. 사이클마다 `DONE`을 지우고, planner가 PRD 전체를 코드와 대조해야만 다시 만들 수 있다. "TASKS가 다 체크됨"은 종료 근거가 아니다.

#### v1의 한계를 v2가 어떻게 고쳤나
| v1의 결함 | v2의 대응 |
|---|---|
| 비용을 관측하지 못함, 금액 상한 없음 | `--output-format json`으로 실행마다 비용·토큰을 `USAGE.csv`에 기록. **누적 상한**과 **에이전트 1회 상한**을 두고, 실행 **전에** `누적 + 1회 상한 > 총 상한`이면 막는다(HALT) |
| 실패를 로그만 남기고 넘김 | 결과를 `SUCCESS`/`BUDGET_LIMIT`/`TURN_LIMIT`/`ERROR`/`TIMEOUT`/`INVALID_RESULT`로 분류해 처리. 연속 오류는 HALT. HALT는 사유·상세·사이클·재개 방법 네 줄로 쓴다 |
| 평가 메모가 새 작업을 폭주시킴 (22개 중 11개가 보강) | PASS의 메모는 **BACKLOG에 쌓기만** 한다. 마일스톤을 마감할 때 `[결함]`만 최대 2개 작업으로 올린다. 실제로 pomodoro-todo에서 결함 2건만 승격됐고 보강 메모 60건은 쌓기만 했다 |
| 문서가 계속 커짐 (TASKS 85KB) | 끝난 마일스톤은 `docs/archive/`로 옮기고 TASKS에는 한 줄 요약만 남긴다 |
| 중단하면 이어받기 어려움 | `.cycle_count`와 `USAGE.csv`로 이어서 한다. 같은 번호의 사이클이 중단됐다면 **이미 성공한 역할은 건너뛴다** |

#### pomodoro-todo 실행에서 드러난 결함과 수정
처음부터 한 번에 돌리지 않고, `max_iterations`를 작게 줘서 **몇 사이클마다 로그를 읽고 의도대로 동작했는지 점검**하며 진행했다. 점검에서 하네스 결함 네 가지를 찾아 고쳤다.
| 증상 | 원인 | 수정 |
|---|---|---|
| JOURNAL 요약에 "작성을 마쳤습니다" 같은 군말이 들어감 | 결과 텍스트의 **첫 줄**을 요약으로 씀 | **마지막 내용 있는 줄**을 씀(0015) |
| evaluator가 타입 검사를 안 돌리고 generator의 보고를 믿음 | 허용 목록에 명령이 없었고, 프롬프트도 "테스트 명령만"이라고 함 | 허용 목록과 프롬프트 명령 표에 빌드 명령 추가 |
| 예산 HALT가 generator와 evaluator 사이에서 나면, 재개 때 그 항목이 평가 없이 넘어감 | 중단된 사이클의 성공한 역할을 기억하지 않음 | 성공한 역할을 `USAGE.csv`로 복원해 이어서 한다(0016). 사람이 손으로 건너뛰게 하면 의미가 없다고 보고 근본 수정함 |
| `[결함]` 분류가 헐거워 승격 장치가 한 번도 안 돎 | 결함 기준이 모호해 연결 누락 같은 것도 `[보강]`으로 분류됨 | 근거(파일:줄), 회귀 위험, REVIEW당 최대 2개로 기준을 고침. 이후 승격이 처음 동작 |
- **예산 HALT는 의도대로 동작한 것**이다. "예산을 넘어 멈췄다"가 아니라 "넘기 전에 막았다"를 확인했다.
- 중간 점검 방법 자체가 배운 점이다. 이 결함들은 단위 테스트(가짜 `claude`)로는 못 잡았고 **실제 실행의 JOURNAL·USAGE·REVIEW를 읽어야** 보였다.

#### 사람이 확인해서 찾은 것과 PRD로 개선
- evaluator는 브라우저를 못 띄워 **화면 점수는 코드를 읽은 추정**이다. 사람이 앱을 직접 눌러 보니 화면·입력·타이머·새로고침 복원·드래그는 정상이었지만, **키보드(Tab)로는 집중을 시작할 수 없었다.** PRD에 키보드 요구가 없었기 때문에 하네스는 만들지 않았고 `[보강]` 메모로만 남겼다.
- PRD의 P1 행에 한 줄(`(개선) 키보드만으로도 집중을 시작할 수 있어야 한다(Tab으로 포커스, Enter 또는 Space로 시작)`)을 추가하고 다시 돌리니, planner가 `DONE`을 지우고 새 마일스톤(M6)과 작업(T32)을 만들었고, generator가 구현했으며, planner가 다시 `DONE`을 만들었다. **2사이클, 약 $1.** 완료 후 개선은 PRD를 고쳐 같은 명령으로 다시 돌리면 된다.

#### 배운 점
| 배운 점 | 내용 |
|---|---|
| 평가자는 보고를 믿지 않는다 | evaluator가 IMPL.md 대신 테스트와 `vue-tsc`를 직접 돌린다. 단 허용 목록과 프롬프트가 둘 다 허용해야 한다(위 수정 참고) |
| 상한은 실행 전에 막는다 | 한도를 넘고 나서 알면 이미 늦다. 에이전트 1회분만큼 넘칠 수 있으니 총 상한에 여유를 둔다 |
| 기록은 에이전트에게 맡기지 않는다 | JOURNAL·비용 기록은 코드가 쓴다. 형식이 흔들리지 않고 실패한 실행도 남는다 |
| 중단과 재개를 설계에 넣는다 | 예산이나 오류로 멈추는 것은 정상이다. 멈춘 곳에서 이어받지 못하면 사람이 개입해야 해서 무인 루프의 의미가 없다 |
| 보강은 쌓고, 결함만 올린다 | 평가 메모를 모두 작업으로 만들면 사이클이 끝없이 늘어난다. 쌓아 두고 마감 때 결함만 골라 올린다 |
| 완료는 `DONE` 파일로, 그래도 사람이 본다 | `DONE`과 "최대 반복 도달"은 종료 코드가 같다(둘 다 0). 파일 유무로 구분하고, 화면은 사람이 확인한다 |
| 루프는 입력(PRD)을 넘지 못한다 | 요구가 없으면 만들지 않는다. 개선은 PRD에 한 줄을 추가하는 것으로 시작한다 |
| 처음엔 작게 돌려 보며 점검 | 한도를 작게 두고 3~5사이클마다 로그를 읽어 의도대로인지 확인했다. 비용도 줄고 결함도 일찍 찾았다 |

#### 한계와 아직 확인하지 못한 것
- **FAIL → 재작업 루프는 실제 실행에서 한 번도 돌지 않았다.** 23번 모두 PASS 또는 조건부였고, 이 경로는 단위 테스트로만 검증됐다. 더 어려운 프로젝트에서 가장 먼저 볼 부분이다.
- **PRD 없이 시작하는 Bootstrap**(대화형 planner)과 **합의 불발 HALT**, **macOS 실행**은 직접 확인하지 못했다. 실행은 `./gradlew run`이 아니라 `installDist`로 만든 실행 파일을 터미널에서 쓴다(`run`은 터미널 입력을 연결하지 않아 Bootstrap이 실패한다).
- evaluator의 한계: 브라우저가 없고 변이 검증도 못 한다. planner는 Bash가 없어 `docs/decisions/*.md`를 지우지 못하고 남긴다.
- 대상 환경(Node 등)을 하네스가 사전 점검하지 않는다. 없으면 약 3사이클을 쓰고 `BLOCKED` → HALT로 끝날 가능성이 크다.
- 위험 명령 차단 훅과 Bash 허용 목록 훅은 보류했다(쓰기 명령은 이미 거부되고, 읽기 전용 명령은 목록 밖이어도 실행된다).
- 비용은 CLI가 보고한 API 환산값이다. Pro 크레딧 차감액과의 비교(보정)는 한도를 다 쓴 상태가 필요해 못 했다.
